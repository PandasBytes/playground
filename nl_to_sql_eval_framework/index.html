THE LOOP CLOSES WHEN
A confirmed failure is gold-labeled and injected back into the offline golden dataset.
THE LLM NEVER SEES YOUR DATABASE
It only sees what RAG puts in its context window. If the right tables are not in that context, no amount of prompt engineering or model capability can compensate. RAG is not a preprocessing step — it is the information supply chain for the LLM.
BUSINESS CONTEXT MUST STAY CURRENT
Schema docs are the vocabulary RAG uses to understand your domain. When tables are renamed, columns added, or clinical definitions change — and schema docs are not updated — retrieval quality degrades silently. This is a people and process problem as much as a technical one.

HOW A RETRIEVAL FAILURE CASCADES
Stage What happens when retrieval fails
RAG misses the correct table The schema for that table is never placed in the LLM context window
LLM generates SQL without it Model either (a) hallucinates the missing table by name, or (b) uses a different real table that seems related — both produce wrong SQL
SQL executes If hallucinated: SQL execution error (visible). If wrong table: SQL executes silently and returns wrong data (invisible).
Response synthesised Model synthesises a confident natural language response from wrong data — no indication anything went wrong
Analyst acts on result Decision made on wrong population count, wrong metric, wrong cohort. Downstream consequences depend on what the analyst does with it.
THE THREE RAG METRICS — WHAT THEY MEASURE AND WHY THEY MATTER
Context Recall
Target ≥ 0.80 · treat as critical
Of all schema elements needed to answer this query, how many did RAG actually surface?
Analogy: you asked a librarian for books on a topic and they returned 3 of 5 relevant books. ContextRecall = 3/5 = 0.60.
Bad score means:
Fix retrieval config, update schema docs, check embedding quality. This is a retrieval problem, not a model problem.
Context Precision
Target ≥ 0.65 · degrades generation quality
Of all schema elements RAG returned, how many were actually relevant to this query?
Analogy: the librarian returned 10 books but only 3 were relevant. ContextPrecision = 3/10 = 0.30.
Bad score means:
Retrieval is too broad. Tighten similarity threshold, add domain filters, improve schema doc specificity.
Faithfulness
Target ≥ 0.80 · synthesis step
Does the final prose response accurately reflect what the SQL actually returned?
Example: SQL returns count: 1,247. Response says "approximately 1,200." That is a faithfulness violation.
Bad score means:
Response synthesis prompt needs constraints. Instruct model to quote numeric results directly and flag empty result sets.
DIAGNOSTIC DECISION TREE — RETRIEVAL FAILURE VS GENERATION FAILURE
Step 1: Did the SQL execute?  NO → syntax error or hallucinated identifier. Run sqlglot.  YES → continue.
Step 2: Is the SQL schema-faithful?  NO, hallucinated → generation failure. Fix retrieval config or add few-shot examples.  YES → continue.
Step 3: Was the needed table in retrieved context?  NO → retrieval failure. Update schema docs, tune embedding similarity.  YES → continue.
Step 4: Does execution accuracy match reference SQL?  NO → generation failure with correct schema. Wrong JOIN, filter, or aggregation (failures 6–11).  YES → continue.
Step 5: Does Ragas Faithfulness pass?  NO → response synthesis failure. Fix prose constraints.  YES → query handled correctly end to end.
Steps 1–3 are automatable with sqlglot and the retrieved_schema trace field. Steps 4–5 require a reference SQL or Ragas/G-Eval. This is why logging retrieved_schema per trace is non-negotiable — without it, Step 3 is not answerable.
KEEPING SCHEMA DOCS CURRENT — A PROCESS REQUIREMENT, NOT JUST A TECHNICAL ONE
ContextRecall declining over 7 days: Retrieval is missing more tables. Check: was schema updated without updating docs? Is a new query type emerging that RAG isn't handling? Action: update schema docs, add new domain to retrieval config.
ContextPrecision declining over 7 days: Retrieval is surfacing more noise. Check: was the schema expanded? Are new tables appearing that don't need to be indexed? Action: tighten similarity threshold, prune stale schema docs.
Both metrics healthy but semantic failures rising: Retrieval is working correctly — the failure is in generation. The fix is in the prompt or domain definitions, not the retrieval config. Don't touch schema docs when the problem is the model.

LEVEL 3 — THE RISKS WE ARE SOLVING FOR
Deterministic → probabilistic
Traditional software: same input, same output, every time. Unit tests work. LLMs: same input, different output every run. Unit tests don’t apply.
Vibe checks don’t scale
Five queries that look good is not evidence — it’s a sample size of five. Failure modes are rare, subtle, and won’t surface until you’re at scale or in production.
No stack trace by default
Traditional system breaks: you have a stack trace. LLM pipeline breaks: you know something went wrong, not where or why. Without a formal harness, you’re debugging a black box with no instruments.
The real-world pattern: Amazon’s Rufus AI shopping assistant was jailbroken with minimal effort — researchers bypassed its scope restrictions, extracted system prompts, and got it to answer questions far outside its intended domain. The model likely scored well on safety benchmarks. The application layer was the point of failure. Scope drift, tool misuse, guardrail bypass, and behavioral inconsistency are application-layer failures. Model benchmarks are not designed to catch any of them.

01 Overview — MVP vs Scale-up: which tier are you in?
Tier 1 · MVP Tier 2 · Scale-up ▼
Tier 1
MVP
"Can we trust this system?"
You're doing this manually. The goal is to find out if the system is even working before you invest in automation.
· 5–20 hand-curated cases
· Run pipeline manually or from a notebook
· Read every output yourself
· Score by hand — right tables? right answer? right response?
· One domain expert as the judge
· Dataset lives in a spreadsheet or flat file
Stop here if the system isn't working yet. Don't build infrastructure around a broken pipeline.
Tier 2
Scale-up
"Can we ship this confidently and repeatedly?"
You've validated the system works. Now you're automating the gate so you can move fast without breaking things.
· 50–200+ cases with structured dimensions
· Automated scoring — assertions first, semantic scoring later
· Runs on every meaningful pipeline change
· Regression blocking — a failing eval blocks the deploy
· Score direction matters more than score value
· Production failures fed back in automatically
Only build this once MVP confirms the system is worth automating. CI/CD around a broken pipeline is just faster failure.

03 Step-by-step — 4 phases, 13 steps, what to do on day one
🤖 LLM 👤 Human ⚙ CI/CD ▼
🤖 LLM can be bootstrapped or scaled with an LLM
👤 Human requires a domain expert — do not delegate
⚙ CI/CD automates in scale-up tier
PHASE 1 Seed the dataset — start with 5–10 cases, get something running
1 Define dimensions, not just questions 🤖 LLM
Identify axes of variation: query type, complexity, domain, edge cases. Generate dimension tuples first (e.g. simple lookup × pharmacy × no joins), then convert each tuple to a natural language question in a separate prompt. Don't ask an LLM for generic questions — you'll get generic outputs.
2 Write ground truth yourself 👤 Human
For each question: write the correct SQL and the correct answer. An LLM can generate a starter draft to iterate from — but a domain expert must validate every label. Never let the agent output become the ground truth.
3 Run the full pipeline end to end 👤 Human
Run each question through the real agent stack. Capture: generated SQL, retrieved tables, execution result, response. Log everything — this is your first set of traces. Not a mock. The real stack.
PHASE 2 Score and read the results — manual first, always
4 Compare output to ground truth 👤 Human
Did it retrieve the right tables? Does the SQL return the right answer? Does the response match? Score binary: pass or fail. Don't use similarity scores yet — read the output yourself. A score of 7/10 tells you more than a cosine similarity of 0.84.
5 Open coding — read every failure 👤 Human
For each failure, write one sentence: what went wrong and where. Don't categorize yet — just observe. Focus on the first failure in each trace; downstream failures often cascade from it. This is the most important step. Do not skip or delegate.
6 Group failures into a taxonomy 👤 Human 🤖 LLM
After open coding 20–30 traces, an LLM can cluster your notes into proposed categories. Review and validate every grouping — LLMs miss nuance (two categories that look similar may need different fixes). This is your failure taxonomy. Build it from what you saw.
PHASE 3 Fix and retest — write evals for errors you found, not errors you imagined
7 Add regression cases per failure pattern 🤖 LLM
For each failure category, write 1–2 test cases that specifically probe it. An LLM can generate variations given your dimensions. These cases stay in the dataset permanently — they are your regression suite.
8 Fix the cause, not the test 👤 Human
Retrieval miss → update schema docs or retrieval config. Wrong logic → update prompt. Wrong value → add domain definitions. Never change the golden answer to match a wrong output. The test is the truth.
9 Re-run and compare ⚙ CI/CD
Score went up? Good. Did anything that was passing now fail? That's a regression — investigate before shipping. A new version must score better than the previous one on the same dataset. Not just pass in isolation.
PHASE 4 Expand systematically — coverage grows from real failures, not from imagination
10 Add difficulty and coverage dimensions 👤 Human 🤖 LLM
Simple lookups → multi-table joins → aggregations → time filters → out-of-scope. Use the dimension matrix: generate tuples across (query type × complexity × domain), convert to NL. Oversample rare and hard cases — easy cases are already covered.
11 Add hallucination probes 🤖 LLM
Write queries where the correct answer requires a table intentionally absent from the retrieved context. Does the system hallucinate the table, use a wrong one, or gracefully decline? All three are informative. Add adversarial and edge cases your users will eventually find.
12 Add production failures as they surface 👤 Human
Every confirmed production failure gets added with a human-corrected gold label. This is the flywheel closing — the dataset grows from what actually happened, not just what was anticipated. Re-run after every addition.
13 Re-run on every pipeline change ⚙ CI/CD
Prompt changed? Re-run. Schema docs updated? Re-run. New model version? Re-run. The dataset only protects you if you actually run it. Treat a failing eval as a blocked deploy, not a warning.
Key principle from Hamel Husain: Start with error analysis, not infrastructure. Spend 30 minutes manually reviewing 20–50 outputs. Use one domain expert as the quality decision maker. Write evaluators for errors you discover — not errors you imagine. And if you're passing 100% of your evals, you're not challenging the system enough.
The flywheel is the compound return on eval investment. Every confirmed production failure added to the dataset means the next deploy is tested against something that actually happened — not just something anticipated. The gate ensures bad models never complete the loop.
